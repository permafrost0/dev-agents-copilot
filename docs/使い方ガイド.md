## 1. 全体像

Excel の詳細設計書に加筆した箇所（追加開発の内容）を入力にして、既存の Java（Spring）プロジェクトのソースを変更します。
AI は1段階ずつ「作成役 → 中立なレビュー役」の順に動き、各段階の最後で**人が確認・承認**してから次の段階に進みます。

```
 ⓪ プロジェクト把握（最初の1回だけ）
     既存ソースと設計方針から、書き方の特徴と共通部品の台帳を作る
        │  人が承認
        ▼
 ① 認識合わせ（機能ごと）
     設計書の指示範囲から要件（REQ）を抜き出し、現行ソースの振る舞いと並べる
        │  人が質問（Q）に回答して承認
        ▼
 ② 実装計画
     要件を小さな実装単位（IU）に分け、順番・対象ファイル・お手本のコードを決める
        │  人が承認
        ▼
 ③ 実装（IU ごとに繰り返す）
     1つの IU だけを最小の差分で実装し、レビュー役が差分を判定する
        │  人が Eclipse でビルドして承認 → 次の IU へ
        ▼
 振り返り
     人の回答・差し戻し・手直しから、ナレッジとレビュー観点の更新案を作る
        │  人が採用した案だけ反映
```

利用者は基本的に **進行役（`/proceed <機能名>`）に話しかけるだけ**です。進行役が次にやることを判断し、AI の作業を進め、人の出番になったら止まって「何を読んで、何をすればよいか」を案内します。

### 役割の分担
| 誰が | すること |
|---|---|
| 人 | 設計書と指示書の準備、文書の確認、質問への回答、Eclipse でのビルド、承認・差し戻し |
| 進行役（orchestrator） | 次の段階の判断、専属エージェントの呼び出し、人への案内。成果物は作らず、承認もしない |
| 専属エージェント（10人） | 各段階の作成とレビュー。1人が1つのステップだけを担当する |
| ツール（tools/） | ゲート判定、形式チェック、書き込みの制限、設計書の抽出、状態の記録 |

### 専属エージェント
| 段階 | 作成役 | レビュー役 |
|---|---|---|
| ⓪ | project-profiler（設計思想と共通部品の台帳） | profile-reviewer |
| ① | spec-reader（要件の抽出）、source-investigator（現行ソースの調査） | alignment-reviewer |
| ② | impl-planner（実装計画） | plan-reviewer |
| ③ | implementer（1 IU の実装） | diff-reviewer |
| 振り返り | knowledge-curator | （人が採否を決める） |

## 2. 用語

| 用語 | 意味 |
|---|---|
| 機能名 | 追加開発の単位につける名前。`work/<機能名>/` のフォルダ名になる（例：`落としもの保管場所`） |
| 指示書 | `work/<機能名>/00_instruction.md`。設計書のどのシート・セル範囲を見るかを人が書く。**AI はここに書いた範囲しか見ない** |
| REQ | 要件。設計書の指示範囲から、1項目・1処理・1メッセージ単位で抜き出したもの（`REQ-01`） |
| Q | 質問。設計書が曖昧・矛盾・記載なしのとき、AI は推測せずに Q を起票する（`Q-01`）。人が回答する |
| D | 差異。設計書と現行ソースの食い違い（`D-01`）。現行仕様はソースを正とする |
| IU | 実装単位。1レイヤー×1つの振る舞いくらいの小さな変更（`IU-01`）。③はこの単位で進む |
| 要人判断 | 既存コードから実装方針が決まらない IU。AI は実装せず、人が判断・実装する |
| ゲート | 段階の関門。`profile`（⓪）、`alignment`（①）、`plan`（②）、`IU-01` など（③）。人が承認すると開く |
| 根拠 | すべての記述に付ける出典。`[設計書: ブック/シート!セル]`、`[ソース: パス:行]`、`[方針: ファイル#見出し]` |
| 人が読む文書 | `⓪プロファイル確認.md`、`①認識合わせ.md`、`②実装計画.md`、`③IU-xx.md`。人が確認するのはこれだけ |
| `_ai/` | AI の中間成果物（要件一覧、現行仕様、レビュー結果、差分など）。必要なときだけ見ればよい |

## 3. 初回セットアップ

### 3-1. 必要なもの
- VS Code と GitHub Copilot（Copilot Chat のエージェントモードが使えること）
- Python 3。ターミナルで次が動くことを確認する
  ```
  python --version
  python -c "import openpyxl"
  ```
  エラーなら `pip install openpyxl`
- 対象PJのソース（Eclipse のワークスペース内のフォルダ。pom.xml がある場所）

### 3-2. フォルダを置く
1. このパッケージ一式を作業用のフォルダに置く（例：`C:\work\dev-agents`）
2. `input/設計方針/` に、設計方針ドキュメントやコーディング規約を置く（Markdown・テキストが望ましい。なければ空でもよい）
3. 必要なら `config/project.md` の `exclude`（調査の対象外にするフォルダ）を直す

### 3-3. ソースルートを書いて、ワークスペースを開く
AI がパッケージと対象PJのソースの両方を読めるように、2つのフォルダを1つの VS Code ワークスペースにまとめます。
**対象PJのソースルートを書くのは、パッケージ直下の `dev-agents.code-workspace` の1か所だけ**です。ツール（ゲート判定、形式チェック、書き込みの制限）も、このファイルからソースルートを読みます。

1. `dev-agents.code-workspace` をテキストエディタで開き、`"name": "source"` の `path` を、対象PJのソースルート（pom.xml があるフォルダ）に書き換える。区切りは `/`
   ```jsonc
   "folders": [
     { "name": "agents", "path": "." },
     { "name": "source", "path": "C:/pleiades/2026-06/workspace/lostitem" }
   ],
   ```
2. VS Code の「ファイル → ファイルでワークスペースを開く」で、このファイルを開く
3. 「このフォルダの作成者を信頼しますか」と聞かれたら、信頼する（フックを動かすため）

> - `"name": "source"` は変えないでください（ツールはこの名前でソースルートを探します）
> - **1つ目のフォルダはパッケージ（`"path": "."`）のままにしてください。** ツールとフックは1つ目のフォルダで実行されます。逆にすると「can't open file 'tools/…'」というエラーになります
> - 対象PJを切り替えるときも、この `path` を書き換えて開き直すだけです

### 3-4. Copilot の準備を確認する
1. Copilot Chat を開き、モードを **エージェント（Agent）** にする
2. チャット入力欄で `/` を打ち、`proceed`、`spec-extract` などのコマンドが出ることを確認する
3. エージェントの選択欄に `orchestrator` などが出ることを確認する
4. モデルは、使える中で推論の強いものを選ぶ（読む量が多く、根拠の正確さが求められるため）

> コマンドやエージェントが出ない場合は、VS Code と Copilot 拡張を更新してください。

### 3-5. ⓪ プロジェクト把握（初回だけ）
チャットで次を実行します。

```
/proceed _profile
```

進行役が project-profiler と profile-reviewer を動かし、承認待ちで止まります。案内に従って次の3つを確認します。

- `work/_profile/⓪プロファイル確認.md`：AI レビューの結果と、人が確認すること
- `knowledge/project_profile.md`：技術構成、レイヤー構成、トランザクション・例外・入力チェック・メッセージ・ログ・命名の書き方
- `knowledge/common_components.md`：共通部品の台帳（以降の実装で「同じ処理を自前で書かない」ための基準）

問題なければ、`⓪プロファイル確認.md` の承認欄を `- [x] 承認` にして、ターミナルで承認します。

```
python tools/gate.py approve _profile profile
```

> 不明点（Q）があれば、`project_profile.md` の『不明点（Q）』に回答を書いてから承認してください。以降のエージェントがすべて参照します。

## 4. 1機能の進め方（進行役を使う）

ここでは機能名を `落としもの保管場所` として説明します。

### 4-1. 設計書と指示書を用意する
1. 加筆済みの設計書（.xlsx）を `input/設計書/` の**直下**に置く（サブフォルダは不可）
2. `work/落としもの保管場所/` フォルダを作り、`templates/00_instruction.md` をコピーして `00_instruction.md` という名前にする
3. 『対象範囲』の表に、加筆したシートとセル範囲を書く

```markdown
| 設計書ファイル | シート名 | セル範囲 | 補足 |
|---|---|---|---|
| 詳細設計書（落としもの）.xlsx | 【落としもの登録】画面項目定義 | A3:H3, A12:H14 | 保管場所の項目を追加 |
| 詳細設計書（落としもの）.xlsx | メッセージ一覧 | A3:D3, A20:D20 | |
```

指示書を書くときのコツ：
- **表の見出し行（列名の行）も範囲に含める**（上の例の `A3:H3`）。含めないと、AI は「20」が桁数なのか何なのか分からず、質問になります
- 加筆していない行は含めない。AI は範囲に入っているものをすべて「今回の変更」として扱います
- 結合セルは、左上のセルが範囲に入るように指定する
- 「上記参照」「同上」のように範囲外を見ないと分からない記述は、AI が質問にします。必要なら、参照先も範囲に加えてください
- シート名とファイル名は、Excel の表示と1文字も違わないように書く（全角・半角、括弧に注意）
- 『補足』の欄やファイル末尾の『補足』は、AI への説明です。範囲を広げる効果はありません

### 4-2. 進行役に依頼する
```
/proceed 落としもの保管場所
```

進行役は次のように動きます。

1. `python tools/gate.py next 落としもの保管場所` で、次にやることを確認する
2. AI の番なら、担当のエージェントをサブエージェントとして呼ぶ（別のコンテキストで動くので、レビュー役は作成役の考えを見ずに判定できる）
3. 終わったら 1 に戻る。AI のレビューが NG なら作成役に直させる（AI 同士は最大2往復）
4. 人の番になったら止まって、案内を出す

止まったときの案内は、たとえば次のようになります。

```
今回行ったこと
- spec-extract → 形式チェック OK（REQ 5件、Q 2件）
- current-survey → 形式チェック OK（D 1件）
- alignment-review → 判定 OK

## 次の操作（gate.py next）
- 種別: 人
- 状況: AI レビューが OK になり、人の承認待ちです
- 人が読むもの: `work/落としもの保管場所/①認識合わせ.md`
- 人の操作:
  1. `work/落としもの保管場所/①認識合わせ.md` を確認する
  2. 質問（Q）の『回答』列に記入する（未回答があると承認できない）
  3. 『承認』欄の `- [ ] 承認` を `- [x] 承認` にする
  4. `python tools/gate.py approve 落としもの保管場所 alignment`（直させたい場合は `python tools/gate.py reject 落としもの保管場所 alignment "理由"`）
  5. もう一度、進行役に依頼する
```

### 4-3. 人の操作をして、また依頼する
案内のとおりに確認・記入・承認をしたら、もう一度 `/proceed 落としもの保管場所` を実行します。これを繰り返すと、①→②→③（IU-01, IU-02, …）→振り返りと進み、最後に「この機能は完了しています」と表示されます。

> 1回の依頼で進行役が動かすのは、最大8ステップです。上限で止まった場合も、もう一度依頼すれば続きから進みます。
> 新しいチャットで依頼しても、続きから進みます（状態はファイルに記録されているため）。

## 5. 段階ごとに人が確認すること

人が読むのは各段階の文書1つだけです。根拠（`[設計書: …]`、`[ソース: …]`）はクリックや検索でたどれるので、気になるところだけ一次情報を確かめてください。

### ⓪ プロファイル確認
| 見るところ | 確認すること |
|---|---|
| 技術構成・レイヤー構成 | 実際の構成と合っているか |
| 書き方（例外、メッセージ、ログなど） | 「全体でこうしている」と言い切っている箇所が、本当に全体の慣習か（1〜2か所の例からの一般化に注意） |
| 共通部品の台帳 | 重要な共通部品が漏れていないか。用途の説明が正しいか |
| 不明点（Q） | 回答できるものは回答を書く |

### ① 認識合わせ（`①認識合わせ.md`）
| 見るところ | 確認すること |
|---|---|
| 対象範囲 | 指示書の範囲どおりか |
| 要件一覧 | 加筆した内容がすべて REQ になっているか（漏れ・余分）。『変更後』が設計書の記載どおりで、AI の解釈が入っていないか |
| 現行（ソース） | 現行の振る舞いの説明が合っているか。「該当なし（新規）」の判断が正しいか |
| 対象外 | 扱わないとしたものが妥当か |
| 質問（Q） | **すべての Q の『回答』列に記入する**（未回答があると承認できない）。回答は、AI がそのまま判断基準にできるように具体的に書く（例：「新規追加。ID は E0012」） |
| 差異（D） | 設計書と現行ソースの食い違い。基本は現行（ソース）のとおり。設計書どおりに直したい場合は、Q の回答や差し戻しで伝える |

### ② 実装計画（`②実装計画.md`）
| 見るところ | 確認すること |
|---|---|
| 実装単位一覧（表の行の順＝実装の順） | 依存される側（メッセージ・Mapper など）から並んでいるか。1つの IU が大きすぎないか |
| 実装予定の箇所・対象ファイル | 変えるべきファイルが入っているか。**ここに書かれたファイル以外は、③で変更できません** |
| 再利用する共通部品 | 既存の部品で済むのに新しく書く計画になっていないか |
| 参照実装 | お手本にするコードが、同じレイヤーの同種の処理か |
| AI実装可否 | 『要人判断』の理由に納得できるか。AI に任せてよいものが要人判断になっていないか |
| テスト観点 | 後の単体テストで使う観点として妥当か（`test_viewpoints.md` にも記録される） |

### ③ 実装（`③IU-xx.md`）
| 見るところ | 確認すること |
|---|---|
| 判定・指摘 | AI レビューの結果。範囲外の変更が1件でもあれば NG になっている |
| 変更一覧 | IU の内容どおりか |
| 差分（`_ai/IU-xx/diff.md`） | **変更一覧以外の変更がないか**（整形、import の並べ替え、コメントの変更など）。書き方が周りのコードと揃っているか |
| ビルド | Eclipse で `maven clean install`。画面に関わる変更なら Tomcat で動作確認 |

承認欄の書き方：
````markdown
## 承認
- [x] 承認
- ビルド結果: 成功
- エラー全文:
```text
```
- 手直しした内容: 変数名を既存に合わせて hokanBashoCd に変更
- 差し戻し理由:
````
- 『ビルド結果』は `成功` か `失敗` のどちらかにする（`成功` でないと承認できない）
- 人が手で直した場合は『手直しした内容』に書く。振り返りで、次から同じ手直しが要らないようにナレッジ化されます
- 項目名（ビルド結果、エラー全文、手直しした内容、差し戻し理由）は変えない（ツールが読み取ります）

### 振り返り（`_ai/retro.md`）
提案ごとに、反映先・内容・根拠が書かれています。採用するものだけ `- [ ] 採用` を `- [x] 採用` にして、進行役に依頼すると反映されます。1回の事例を一般化しすぎている提案は採用しないでください。

## 6. 人が行う操作（承認・差し戻し・やり直し）

承認などの操作は、**人が VS Code のターミナルで**実行します（AI には実行させません）。
ターミナルは「表示 → ターミナル」で開きます。ワークスペースのフォルダを聞かれたら `agents`（パッケージ）を選びます。

| 操作 | コマンド | 使う場面 |
|---|---|---|
| 承認 | `python tools/gate.py approve <機能名> <ゲート>` | 文書を確認し、承認欄に `[x]` を付けた後 |
| 差し戻し | `python tools/gate.py reject <機能名> <ゲート> "理由"` | AI に直させたいとき。理由は具体的に（AI はこれだけを見て直す） |
| やり直し | `python tools/gate.py reopen <機能名> <ゲート>` | 承認済みの段階を作り直したいとき、形式エラーで止まったとき |
| 状態の確認 | `python tools/gate.py status <機能名>` | 各ゲートの状態を一覧で見る |
| 次の操作の確認 | `python tools/gate.py next <機能名>` | 次に誰が何をするかを見る（状態は変わらない） |
| 中断の解除 | `python tools/gate.py cancel` | エージェントが途中で止まり、書き込みが拒否されるようになったとき |

ゲート名は `profile`（⓪）、`alignment`（①）、`plan`（②）、`IU-01` など（③）。⓪の機能名は `_profile` です。

例：
```
python tools/gate.py approve 落としもの保管場所 alignment
python tools/gate.py reject 落としもの保管場所 IU-02 "既存の LostItemValidator を使ってください"
python tools/gate.py reopen 落としもの保管場所 plan
```

承認できないときは、理由が表示されます（承認欄のチェック漏れ、未回答の Q、ビルド結果が `成功` でない、など）。

## 7. 個別コマンドで進める場合

進行役を使わずに、ステップごとにコマンドを実行することもできます。AI の作業を1ステップずつ見ながら進めたいときに使います。

| 段階 | コマンド（この順に実行） |
|---|---|
| ⓪ | `/project-profile` → `/profile-review` |
| ① | `/spec-extract <機能名>` → `/current-survey <機能名>` → `/alignment-review <機能名>` |
| ② | `/impl-plan <機能名>` → `/plan-review <機能名>` |
| ③ | `/implement-unit <機能名> IU-01` → `/diff-review <機能名> IU-01`（IU ごとに繰り返す） |
| 振り返り | `/retrospect <機能名>` → 採否にチェック → `/retrospect <機能名> --apply` |

修正のときは、作成役のコマンドに付けて実行します。
- `--fix-review`：AI レビューの指摘、または人の差し戻し理由だけを直す
- `--fix-build`：③IU-xx.md に貼ったビルドエラーだけを直す（`/implement-unit <機能名> IU-xx --fix-build`）

注意：
- **コマンドごとに新しいチャット（New Chat）を開いてください。** 同じチャットで続けると、レビュー役が作成役のやり取りを見てしまい、中立なレビューになりません
- 順番を飛ばすと、エージェントは最初のゲート判定で止まります（「先に /spec-extract を実行してください」など）。迷ったら `python tools/gate.py next <機能名>` で確認できます
- 進行役と個別コマンドは混ぜて使えます（状態は共通です）

## 8. 状態の確認と読み方

`python tools/gate.py status <機能名>` の表示例：

```
# 状態: 落としもの保管場所
| ゲート | 状態 | AIレビュー往復 | 人の差し戻し |
|---|---|---|---|
| alignment | 承認済み | 1 | 0 |
| plan | 承認済み | 0 | 0 |
| IU-01 | 承認待ち | 0 | 0 |
```

| 状態 | 意味 | 次にすること |
|---|---|---|
| 未着手 | まだ始まっていない | 進行役に依頼 |
| AI作成済み（レビュー待ち） | 作成役が終わった | 進行役に依頼（レビュー役が動く） |
| レビューNG（修正待ち） | AI レビューが NG、または人が差し戻した | 進行役に依頼（作成役が直す） |
| 承認待ち | AI レビューが OK | 人が文書を確認して承認 |
| AIレビュー上限到達（人の判断待ち） | AI 同士で2往復しても OK にならなかった | 人が指摘を読み、差し戻すか承認する |
| 中断（質問の回答待ち） | ③で対象ファイル外の変更が必要などで、実装が止まった | `_ai/IU-xx/impl.md` の質問に回答して進行役に依頼。または計画を見直す |
| 形式エラー（人の確認が必要） | 成果物の形式チェックが3回通らなかった | `status.json` の history で原因を見て、`reopen` |
| 承認済み | ゲートが開いた | 次の段階へ |

### ファイルの場所
```
work/<機能名>/
  00_instruction.md        人が書く指示書
  ①認識合わせ.md          人が読む（①）
  ②実装計画.md            人が読む（②）
  ③IU-01.md               人が読む（③）
  test_viewpoints.md       テスト観点（後の単体テストで使う）
  status.json              状態（ツールだけが更新する。手で編集しない）
  _ai/
    extract/               設計書の抽出結果（指示範囲だけ）
    01_requirements.md     要件一覧
    02_current_spec.md     現行仕様
    review_①.md, review_②.md   レビュー結果
    IU-01/
      impl.md              実装メモ（変更箇所と根拠）
      diff.md              IU 開始前からの累積差分
      edits.md             編集ごとの記録（フックが有効な場合）
      review.md            差分のレビュー結果
      before/              IU 開始前のファイル（差分の基準）
    history/               人が読む文書の旧版（回答の消失チェックに使う）
    retro.md               振り返りの提案
```

## 9. ナレッジと振り返り（使うほど良くなる仕組み）

`knowledge/` には、人の判断が蓄積されます。全エージェントが参照しますが、**設計書やソースより優先はしません**。

| ファイル | 中身 | 増え方 |
|---|---|---|
| project_profile.md | 設計思想・書き方 | ⓪で作成。人が承認 |
| common_components.md | 共通部品の台帳 | ⓪で作成。人が承認 |
| qa_log.md | 過去の質問と回答 | 振り返りで人が採用したもの |
| glossary.md | 設計書の用語 ↔ ソース上の名前 | 同上 |
| source_map.md | 機能・画面 → 関連ソース | 同上 |
| conventions.md | 方針ドキュメントにない暗黙の書き方 | 同上（人の手直しから） |
| pitfalls.md | 見落としやすい点 | 同上（ビルドエラー・差し戻しから） |
| CHANGELOG.md | 反映の履歴 | 振り返りの反映時に自動で追記 |
| metrics.csv | 機能ごとの指標（質問数、NG 数、手直し数など） | 振り返りで自動集計 |

- 過去の回答に当てはまりそうな場合でも、AI は勝手に適用せず「過去の回答 Q-xx と同じ扱いでよいか」と質問します。回答の手間は減りますが、判断は人に残ります
- レビュー役の観点（`.github/steps/<ステップ>/checklist.md`）にも、差し戻しから学んだ観点が追記されます
- エージェント定義そのものの改善案は「エージェント定義（構築環境で反映）」として提案だけされます。採用する場合は、このリポジトリを直して配布し直してください
- `metrics.csv` で、機能を重ねるごとに AI レビュー NG・差し戻し・手直し・ビルドエラーが減っているかを見られます

## 10. 困ったとき

| 症状 | 原因と対処 |
|---|---|
| `/proceed` などのコマンドが出ない | ワークスペースをファイルから開いているか、Copilot がエージェントモードかを確認。VS Code と Copilot を更新 |
| 「【ゲート判定 NG】⓪プロジェクト把握が未承認です」 | 先に `/proceed _profile` で⓪を終わらせる |
| 「ワークスペースファイル（dev-agents.code-workspace）がパッケージ直下にありません」「path がひな形のままです」「path のフォルダが存在しません」 | `dev-agents.code-workspace` の `"name": "source"` の `path` を確認（区切りは `/`、フォルダが実在すること） |
| 「00_instruction.md の『対象範囲』表が空です」 | 指示書の表の書式（4列、見出し行と区切り行）を確認 |
| 「設計書が見つかりません」「シートが見つかりません」 | 設計書が `input/設計書/` の直下にあるか。ファイル名・シート名が完全に一致しているか |
| 「指示された対象範囲の外を参照しています」で形式チェックが通らない | AI が範囲外のセルを根拠にした。範囲が足りないなら指示書に加えて `reopen <機能名> alignment` |
| 承認できない | 表示された理由を確認（承認欄の `[x]`、未回答の Q、ビルド結果が `成功` か） |
| 「can't open file 'tools/…'」 | ワークスペースの1つ目のフォルダがパッケージになっていない |
| 「【ガード】… の作業が始まっていません」 | エージェントが `gate.py check` の前に書き込もうとした。もう一度依頼すれば通常は直る |
| エージェントが途中で止まり、その後ほかのチャットでも書き込みが拒否される | `python tools/gate.py cancel` で実行中のステップを閉じる（3時間たつと自動で無効になる） |
| 進行役が同じステップを繰り返して止まる | `python tools/gate.py status <機能名>` と、該当ステップの `_ai/` のファイルを確認。必要なら `reject` で理由を伝えるか `reopen` |
| AI レビューが上限到達になった | 指摘（`_ai/` のレビュー結果）を読み、直させるなら `reject "理由"`、問題なければ承認欄にチェックして `approve` |
| ③で「要人判断」と言われた | 人が実装してビルドを確認し `approve <機能名> IU-xx`。または方針を決めて `reopen <機能名> plan` し、②の Q や差し戻し理由で方針を伝える |
| 実装に計画外のファイルの変更が必要だった | `_ai/IU-xx/impl.md` の『## 中断』に質問が出る。計画を直すなら `reopen <機能名> plan` → 進行役に依頼（②からやり直し） |
| サブエージェントが動かない | Copilot Chat の「ツールの構成（Configure Tools）」で、サブエージェントの実行（Run Subagent）が有効か確認 |
| ターミナルのコマンドで毎回確認が出る | `.vscode/settings.json`（またはワークスペースファイルの settings）の `chat.tools.terminal.autoApprove` が読まれているか確認。承認・差し戻しのコマンドは、わざと対象外にしている |

## 11. よくある質問

**Q. 人が承認するとき、どこまで細かく見ればよいですか？**
A. 人が読む文書（①②③）を見て、根拠が気になる箇所だけ一次情報（設計書・ソース）を開いてください。根拠の実在や形式はツールと AI レビューが確認済みです。人が見るべきなのは「解釈が正しいか」「やりたいことと合っているか」です。

**Q. AI に直してほしいことを伝えるには？**
A. `python tools/gate.py reject <機能名> <ゲート> "理由"` で差し戻します。理由は、AI がそれだけを読んで直せるくらい具体的に書いてください（例：「REQ-03 の桁数は設計書の F14 の 20 を使う」）。①なら Q の回答で伝えることもできます。

**Q. 自分で直したほうが早いときは？**
A. ③では、人が対象ファイルを直してから承認しても構いません。そのときは承認欄の『手直しした内容』に書いてください。振り返りで、次から同じ手直しが要らないようにナレッジになります。①②の文書を手で直すと、次に AI が作り直したときに上書きされるため、差し戻し理由や Q の回答で伝える方が確実です。

**Q. 途中で別の機能を始めてもいいですか？**
A. できます。状態は機能ごとに `work/<機能名>/` に記録されています。ただし、同時に2つのチャットで AI を動かすのは避けてください（実行中のステップは1つだけ記録されるため）。

**Q. 設計書を差し替えたら？**
A. ①から作り直します。`python tools/gate.py reopen <機能名> alignment` → 進行役に依頼。②以降が承認済みなら、それぞれ `reopen` が必要です。

**Q. フックが使えない環境ではどうなりますか？**
A. 段階の進行（ゲート判定）、形式チェック、状態の更新、差分の記録はそのまま動きます。書き込み先の制限など一部が「指示で守らせる」形になり、範囲外の変更はレビュー役と人の差分確認で見つけることになります（[README の『守られていること』](../README.md#守られていること)）。

**Q. 会社のリポジトリにある設計書を、このリポジトリに入れてもいいですか？**
A. 入れないでください。`input/` と `work/` の中身は `.gitignore` で除外していますが、`knowledge/` は使うと PJ の情報が追記されます。公開リポジトリには、使い始める前の状態だけを置いてください。
